# mise-hub 设计文档

日期：2026-10-19
状态：待评审（构建者检查中）

---

## 1. 意图

给 **mise** 做一个图形界面，用 Rust + GPUI 实现。目标用户是「已经在用或想用 mise、但记不住命令」的开发者。

真正的价值不是把命令行按钮化，而是**把 mise 的可发现性还给人**。

为什么现在做：mise 已经具备完整能力（本机为 `2026.10.13 macos-arm64`，registry 收录 1067 个工具别名，`search` 支持模糊匹配和跨 npm/cargo/gem/dotnet 源搜索），但这些能力全部埋在命令行里，命令名本身就是要背的负担。真实体验是：心里有个需求，找不到入口，只能去搜网页或问 AI，绕一圈回来才敲命令。

这个 App 让用户能**逛**、能**搜**、能**看懂**、能**执行**，而不需要记住任何命令。

---

## 2. 目标 / 非目标 / 反目标

### 目标

1. **发现**：不记命令也能找到 mise 支持的工具，看到它是什么、能干什么、有哪些版本。
2. **安装**：选版本、安装、看到进度和结果。
3. **看清现状**：知道自己机器上装了什么、哪些是全局的、哪些属于当前项目、两边版本是否冲突。
4. **管理**：升级、卸载、切换全局/项目版本、写回 `mise.toml`。
5. **诊断环境变量**：区分「配置声明」与「实际生效」，并能从最终值追溯来源。
6. **跑任务**：发现任务、看懂依赖、执行、看日志。
7. **跨平台**：优先 macOS，架构上不堵 Windows / Linux。

### 非目标（这一版不做）

- 不做 mise 全部子命令的图形化（`ssh`、`oci`、`daemons`、`dotfiles`、`secrets`、`packslip`、`patrons`、`mcp`、`skills` 等实验性或无关功能不进 GUI）。
- 不做 `mise.toml` 的通用 TOML 编辑器。
- 不做任务定义的完整编辑（依赖、增量、别名等的可视化增删改）——本版只做运行与管理。
- 不做多用户/团队共享的项目配置同步。
- 不自动扫描用户磁盘找项目。

### 反目标（做到这些算失败）

- **变成命令行的皮肤**：每个按钮旁边贴一条 `mise xxx` 让用户自己敲。GUI 要真的把事情做完。
- **假装安装就等于生效**：混淆 `mise install`（装到机器）和 `mise use`（写进配置生效），让用户以为装完就能用。
- **隐藏破坏性操作**：卸载、改配置这类动作必须让用户看清影响范围再执行。
- **启动就卡**：registry 1067 条、多项目、多版本都不应该让界面卡顿或长时间空白。
- **只在开发者自己机器上跑得通**：跨平台是目标，不能写死 macOS 路径和假设。

---

## 3. 约束

- **语言与框架**：Rust + GPUI（用户指定）。
- **数据来源**：一律通过调用用户机器上的 `mise` 可执行文件获取，不重新实现 mise 的逻辑，不直接解析 mise 内部数据结构。
- **发布形态**：要发布给他人使用，需要打包、分发、更新机制。
- **用户环境不可假设**：可能没装 mise、可能版本很老、可能没有 homebrew 装的 mise。

| 决策 | 用户的选择 |

| 任务页定位 | 运行与管理先做扎实：发现任务、理解依赖、执行任务、查看日志 |

| 主题 | 浅色为主 + 深色主题，且要**多套主题供用户切换** |
| 技术选型 | 接受用 `gpui-component`（longbridge/gpui-kit）打底 |
| 分期顺序 | 认可 M0–M5（见第 8 节） |

## 5. 技术判断（这些是我的 call，不是用户拍板的）

用户把技术细节交给了我。以下是我做的选择，请一并检查。

### 5.1 GPUI 版本与组件库

crates.io 上的 GPUI 生态目前分层：

- `gpui` **0.2.2** —— Zed 官方发布在 crates.io 的快照，偏旧
- `gpui-pre` **0.3.9** —— 更新的 Zed 快照（`zed@93d7456`）
- `gpui-base` **0.7.3** —— longbridge/gpui-kit 的基础设施层，依赖 `gpui-pre`
- `gpui-component` **0.7.3** —— 60+ 桌面组件（表格、虚拟列表、弹窗、输入框、标签页、通知、主题系统），依赖 `gpui-base` 与 `gpui-component-macros`、`gpui-kit-assets`

**选择**：以 `gpui-component 0.7.3` 为组件基础，跟随它绑定的 `gpui-base` / `gpui-pre`。

理由：省掉重写表格、虚拟列表、弹窗、主题这些轮子的时间；它的依赖里自带 `rust-i18n`，中文界面现成；主题系统正好满足「多套主题可切换」。

代价：多了一层第三方封装，Zed 上游 API 变动时要等它跟进。

### 5.2 与 mise 的交互方式

**选择**：**子进程调用 mise CLI**，读取其 JSON 输出。不链接 mise 源码，不自己解析 mise 的缓存和配置格式。

理由：mise 是快速迭代的二进制，行为随版本变化；调用 CLI 保证和用户手动敲命令的结果永远一致；`mise.toml` 的语义（继承、多层配置、模板、平台条件）非常复杂，重实现必然出错。

代价：需要把 CLI 的文本输出（少数没有 JSON 的命令）和进度输出解析成结构化数据；需要处理「mise 不存在」「版本过老」两种情况。

### 5.3 数据源映射（已在本机核实）

| 用途 | 命令 | 输出形态 |
|---|---|---|
| 工具索引（发现页数据源） | `mise registry --json` | 1067 条 `{short, backends[], bins[], description, aliases[]}` |
| 已安装工具 + 版本 + 来源 | `mise ls --json` | `{ 工具名: [{version, requested_version, install_path, source:{type,path}, installed, active}] }` |
| 单个工具详情 | `mise tool <名> --json` | `{backend, description, url, installed_versions, requested_versions, active_versions, config_source, tool_options, security}` |
| 可选版本列表 | `mise ls-remote <工具> --json` | `[{version, created_at}]` |
| 可升级项 | `mise outdated --json` | 结构化 map |
| 配置文件清单 | `mise config ls --json` | `[{path, tools[]}]` |
| 生效环境变量 + 来源 | `mise env --json-extended` | `{ 变量名: {source, tool, value} }` |
| 生效环境变量（纯值） | `mise env --json` | `{ 变量名: 值 }` |
| 任务清单 | `mise tasks ls --json` | 数组 |
| 单个任务详情 | `mise task info <名> --json` | 结构化对象 |
| 声明式环境变量（含来源文件） | `mise set` | **文本列表，无 JSON**，每项带来源文件 |
| 写环境变量 | `mise set KEY=VALUE`（`-g` 全局 / `--file` 指定 / `-E` 环境） | 文本 |
| 删环境变量 | `mise unset` | 文本 |
| 模糊搜索 | `mise search <名>` | **只有文本表格，无 JSON** |
| 安装 / 卸载 / 升级 / 应用版本 | `mise install`、`uninstall`、`upgrade`、`use` | 流式文本输出 |

**关于写入配置的规则**：所有写操作一律走 mise 自己的命令（`mise use`、`mise set`、`mise unset`），不直接改 TOML。`mise` 负责处理配置层级、写哪个文件、保持格式。只读展示时如果需要，可以解析 TOML 补足缺失字段，但**绝不用于写入**。

**关于「应用」一个版本**：`mise use` 会安装缺失的版本并写入配置，且支持 `--pin`（写死解析后的版本）/ `--fuzzy`（写请求，如 `20`）/ `--dry-run`（预览改动）。这正好对应「让它生效」这个动作——它允许顺带安装，但不等于「安装」这个动作本身。安装动作只用 `mise install`。

**关于 `mise search` 的判断**：它没有 JSON 输出，且默认行为是「registry + 已安装后端插件 + 必要时查 aqua registry」，需要联网。而 `mise registry --json` 已经包含 `description`、`bins`、`aliases`，足够在本地对 1067 条做模糊搜索。所以**发现页的默认搜索走本地 registry 索引**，不联网、瞬时响应；把 `mise search --all`（联网、跨包源）作为用户显式触发的「深度搜索」入口。

这一点是推测，需要构建者验证：本地 registry 索引的搜索质量是否足够覆盖「带着名字验证」和「带着用途搜」两种场景。

### 5.4 其他实现选择

- **mise 定位**：按顺序探测 `PATH` 中的 `mise`、`~/.local/bin/mise`、`/opt/homebrew/bin/mise`、`/usr/local/bin/mise`；记录探测到的绝对路径并在 App 内固定使用，避免受 shell 环境变化影响。
- **所有 mise 调用都带 `-C <项目目录>`**，让「当前项目」的概念不依赖 App 自身的进程工作目录。
- **异步与并发**：所有 mise 调用走异步任务，结果回到 UI 线程；同一工具的重复请求要合并（用户快速切换列表项时不应重复起进程）。
- **配置读写要有备份**：任何写 `mise.toml` / 全局配置的操作，先备份原文件再写。
- **trust 机制**：mise 要求配置文件被信任才能执行。GUI 需要检测未信任状态并引导用户 `mise trust`，不能静默失败。
- **版本兼容策略**：不按版本号一刀切，而是**启动时探测能力**——逐个尝试本设计依赖的 JSON 命令，记录哪些可用。不可用的功能降级并在界面上说明，同时提示升级 mise。文档里以本机 `2026.10.13` 为已验证基线；低于基线但能力齐全的版本照常工作。
- **工具依赖的呈现**：mise 的工具本身不构成通用依赖图。只展示 `mise tool --json` 里实际存在的 `tool_options.depends`；**不做「被依赖」反查**，因为没有数据源。

## 6. 信息架构与界面

### 6.1 整体骨架

三栏，参照用户提供的 Homebrew GUI 截图：

```
┌──────────────┬────────────────────────────┬──────────────────────┐
│  侧边栏       │  列表区                     │  详情区               │
│              │                            │                      │
│  工作台       │  搜索框                     │  工具详情 / 版本对比   │
│   发现        │  范围筛选器                 │  来源 / 官网 / 后端    │
│   全局·工具   │  「全部 | 本项目 | 全局」    │  depends / 可执行文件  │
│   全局·任务   │   （仅项目页）              │  动作按钮             │
│   全局·环境   │                            │                      │
│              │  列表项                     │                      │
│  项目         │   （名称 + 后端标签 + 版本） │                      │
│   ▾ mise-hub │                            │                      │
│      工具     │                            │                      │
│      任务     │                            │                      │
│      环境     │                            │                      │
│   ▸ blog     │                            │                      │
│   ▸ api      │                            │                      │
├──────────────┴────────────────────────────┴──────────────────────┤
│  底部终端面板（可折叠）                                            │
│  [标签1] [标签2]                       保存 | 复制 | 清除          │
│  ───────────────────────────────────────────────────────────────  │
│  命令输出…                                                        │
└──────────────────────────────────────────────────────────────────┘
```

### 6.2 侧边栏（方案 A）

- 顶层分组：**工作台**（全局）与**项目**。
- 「工作台」下固定四项：**发现**、工具、任务、环境。发现是独立的全局入口，不属于任何项目。
- 「项目」下是可折叠的项目列表，每个项目展开出工具、任务、环境三项。
- 项目由用户手动添加（选择文件夹）；列表持久化保存；支持移除、重命名显示名、拖动排序。
- 项目列表很长时要能折叠分组或滚动，不能把全局那一段挤没了。
- **什么叫一个项目**：用户在 App 里添加的任意文件夹就是一个项目，用规范化后的绝对路径做唯一标识。文件夹里**不要求**已有 `mise.toml`；没有配置时，该项目的工具/任务/环境页显示空状态，并在用户执行「应用」动作时询问是否创建 `mise.toml`。允许添加嵌套的文件夹，但不做去重建议。
- **范围筛选器只出现在项目页**：全局·工具页只显示全局工具，没有筛选器；项目·工具页才有「全部 / 本项目 / 全局」。


### 6.3 工具页

- **列表**：当前范围下的工具，每项显示名称、后端标签（`aqua` / `github` / `asdf` / `vfox` / `npm` / `pypi` / `core` 等）、版本、来源。
- **范围筛选器**：只在项目·工具页出现，`全部 | 本项目 | 全局`。选「全部」时，同一工具如果两边都有，**并排显示两条**并标出哪条当前生效、哪条被覆盖。全局·工具页没有筛选器，直接列出全局工具。
- **详情**：名称、描述、后端、本项目要求的版本、全局版本、实际生效版本、来源配置文件路径、官网、安装路径、`tool_options.depends`（如有）、可用版本列表、动作按钮。
- **动作**：安装指定版本、卸载、升级、切换版本（写进本项目 / 全局）、复制等价命令。

**「安装」与「生效」必须分开**：安装只是把版本放到机器上；要让它在某处生效，是另一个显式动作（写进该项目的 `mise.toml` 或全局配置）。界面上要让这个区别一眼可见——比如装完之后该工具显示为「已安装 · 未生效」，并给出「应用到本项目 / 应用到全局」的按钮。

### 6.4 发现页

**这是这个 App 的核心价值页。**

- 一个搜索框 + 一个列表，数据来自本地 `mise registry --json` 索引。
- 支持三种进入方式，对应三种真实场景：
  - 输入名字 → 模糊匹配（带名字验证）
  - 输入用途词 → 在名称、描述、`bins`、`aliases` 里匹配（带着用途搜）
  - 空搜索 → 浏览（没目的地逛）
- 每一项显示：名称、描述、后端、包含的可执行文件。
- 点击某项 → 拉取可用版本列表（`ls-remote`）→ 用户选版本 → 安装 → 进度在底部终端面板实时滚动。
- 一个显式的「深度搜索」入口，触发 `mise search --all`（联网、跨 npm/cargo/gem/dotnet 包源），结果与本地结果分区展示。
- 已安装的工具在列表里要有状态标记，避免重复安装的困惑。
- **搜索语言**：只支持英文关键词（registry 的 `description` 全是英文）。中文用途词不做本地匹配，也不做中文标签层；需要更广的覆盖时走「深度搜索」。界面上要说明这一点，避免用户以为搜索坏了。

### 6.5 环境变量页（诊断与管理中心）

**核心是把「配置声明」和「实际生效」分开，并支持从结果追溯来源。**

- **两个视角**：
  - 声明：`mise set` 的无参输出（列出每个变量及其来源文件）+ 工具自动注入的变量；每项标明属于全局还是某个项目。
  - 生效：`mise env --json-extended` 给出的最终值与 `source` / `tool` 字段。
- **写入规则**：增删改一律走 `mise set` / `mise unset`（`-g` 全局、`--file` 指定文件），由 mise 决定写哪个配置、如何保持格式。只读展示可以用 TOML 解析补足 `mise set` 没给出的字段，但不用于写入。

- **一张可追溯的表**：变量名、当前值、来源、覆盖链、是否被标记为 redacted。点开一行看到完整覆盖链，而不只是最终值。
- **PATH 特殊呈现**：PATH 这类拼接型变量单独一种视图，展示它由哪几段组成、每段来自哪个工具或配置。
- **差异视图**：项目 vs 全局 vs App 实际拿到的环境，三者对比。
- **管理动作**：新增变量（明确写进哪个范围）、编辑、删除、标记 redact、批量导入。写入前备份。
- **安全提示**：`mise env` 的输出含真实密钥值，界面上要有明确的显示/隐藏控制。

### 6.6 任务页

本版定位是**运行与管理**，不做完整编辑。

- **发现**：列出 `mise.toml` 里的任务，也包含 `mise-tasks/` 目录下的文件任务。每个任务显示名称、描述（`description` 字段）、来源文件、是否隐藏。
- **理解依赖**：把 `depends` 关系画出来（树或图），让用户在执行前就知道会发生什么、按什么顺序发生。
- **执行**：选中任务 → 运行 → 输出进底部终端面板。`watch` 任务要有明显的「正在监听」状态。
- **日志**：底部面板支持多标签（多个任务并行）、保存到文件、复制、清除。要能正确处理 ANSI 颜色和进度条重绘。

### 6.7 配置 / 诊断页

- **没装 mise**：明确的引导页，告诉用户 mise 是什么、怎么装、装完点重新检测。
- **装了 mise**：模仿 Homebrew GUI 的配置页，分组展示：
  - mise 本体：版本、安装路径、安装方式（homebrew / 脚本 / cargo）、是否有更新
  - 环境：`MISE_*` 相关设置、settings 概览
  - 系统：平台、架构、shell、相关工具版本
  - 配置文件：`mise config ls --json` 列出的所有配置文件及其路径
- 提供「复制诊断报告」按钮（便于用户求助）。

### 6.8 主题

- 浅色为主，深色为可切换主题，且支持多套主题。
- 用 `gpui-component` 的主题系统承载；主题定义要能被用户增删，而不只是内置两套。
- 中文界面（`rust-i18n`），语言可切换。

## 7. 关键交互细节

- **启动**：先探测 mise。没有 → 引导页。有 → 进入主界面，恢复上次打开的项目和页面。
- **性能**：registry 索引在后台构建并缓存，界面先出骨架再填充；列表用虚拟滚动；工具多时列表不能卡。
- **进度**：安装/升级/卸载的输出流式写入底部终端面板，要正确处理 ANSI 转义和 `\r` 重绘（进度条）。需要伪终端才能拿到真实进度，这是一个待验证的技术点。
- **失败**：mise 命令失败时，把原始 stderr 完整展示在终端面板里，不要在界面上抽象成一句「失败了」。
- **破坏性操作**：卸载、改配置、删变量都要二次确认，并显示具体影响（会删掉什么文件、哪些项目受影响）。

## 8. 分期

用户已认可这个顺序。

### M0 骨架

GPUI 应用外壳、三栏布局、主题系统（浅色为主 + 深色 + 多套可切换）、中英文、侧边栏方案 A 的导航、手动添加项目并持久化、mise 探测与引导页。

### M1 工具 · 发现与查看

**用户最痛的路径，放在最前面。**

工具列表（含范围筛选器）、工具详情、基于本地 registry 索引的模糊搜索、版本列表、安装、底部终端面板显示进度。

### M2 工具 · 管理

升级（含 `outdated` 页）、卸载、切换全局/项目版本、多版本并存的管理、写回 `mise.toml`、安装与生效的区分。

### M3 环境变量

声明 vs 生效双视图、`--json-extended` 来源追溯、覆盖链、PATH 分段、增删改、差异视图、敏感值处理。

### M4 任务

任务发现（含文件任务）、依赖关系呈现、运行、日志面板、watch 状态。

### M5 收尾

配置/诊断页、打包分发（macOS `.app`，Windows / Linux）、自动更新、文档、i18n 补全。

## 9. 留给构建者的

以下故意不做决定，由构建者按工程判断处理：

- 具体的 crate 组织方式（是否拆 workspace、模块边界）。
- 状态管理方案（GPUI 的 entity/model 如何划分）。
- 本地缓存的格式和失效策略（registry 索引、版本列表的缓存时间）。
- 底部终端面板的终端模拟方案（自研渲染 vs 现成的 PTY + 终端模拟库），以及是否必须支持真正的交互式输入。
- 打包与分发的具体方式（`.app`、dmg、签名、公证、CI）。
- 单元测试与集成测试的边界；mise 调用层的 mock 策略。
- 主题定义的具体文件格式。

## 10. 风险与待验证

1. **伪终端**：`mise install` 的进度条需要 TTY。非 TTY 下输出会退化。需要验证能否既拿到干净的结构化结果，又拿到好看的进度。
2. **本地搜索质量（已定方向）**：本地 registry 只有英文的名称、描述、`bins`、`aliases`。用户已确认搜索只支持英文关键词，中文用途词不做本地匹配，走联网的「深度搜索」。风险降级为「英文意图搜索的召回率是否足够」，需要在 M1 用真实关键词抽样验证。
3. **`gpui-component` 的成熟度**：第三方封装，Zed 上游 API 变动时需要等它跟进。要在 M0 就验证它能满足表格、虚拟列表、主题切换、底部面板这四件事。
4. **`source` 字段的有效性**：本机测试中，全局变量在 `mise env --json-extended` 里的 `source` 是空字符串。需要验证项目级变量能否给出有意义的来源路径——这直接决定第 6.5 节的「追溯来源」能做到什么程度。
5. **跨平台**：GPUI 在 Windows / Linux 上的成熟度和打包体验都弱于 macOS，需要尽早验证，避免架构上写死 macOS。
6. **多项目 × 多范围的组合爆炸**：侧边栏方案 A 在项目很多时会被挤爆，需要提前想好折叠策略。

## 11. 成功的样子

- 环境变量出问题时，能点几下就找到「这个值是谁设的」。
- 全程不需要记住任何 mise 子命令。
